# 人物侧写前置与导演提示词流水线设计

日期：2026-08-13

## 目标

调整“导演时间”的副 API 调用和提示词，使人物侧写先于事件规划完成，并让事件规划稳定产生完整的多阶段大纲。人物侧写和事件规划都必须遵守人物证据隔离与认知迷雾：导演可以掌握幕后资料，但角色只能使用自己已经知道、感知或合理推断的信息。事件类别权重必须真正参与事件规划，而不是只保存在设置中并在模型响应后做本地类别校验。

本次改动不改变核心边界：插件只生成和维护事件大纲、步骤、伏笔与幕后指令；不代替用户发送消息，不在创建事件时直接生成角色正文，不把完整剧本长期注入聊天上下文。

## 用户可见行为

### 副 API 配置

人物侧写、事件规划、阶段准备和反应判断统一使用设置中的独立兼容 API。未配置 endpoint 或 model 时不回退到主 API。

进入或切换单人聊天时：

- 未配置副 API：显示“导演时间还没连接副 API，请先在设置 → 连接中完成配置。”
- 已配置且没有人物侧写：自动开始首次人物侧写。
- 正在侧写：显示“正在生成压缩人物侧写…”。

### 资料变化

角色卡或用户选中的世界书内容的资料指纹变化时，现有侧写标记为 `stale-pending`，不自动调用 API。人物页显示“角色资料有改动，要重新生成侧写吗？”，提供两个按钮：

- “重新生成侧写”：调用副 API，完成后保存新侧写和新的资料指纹。
- “暂时不用”：继续使用现有侧写，记录当前资料指纹为已忽略版本；在资料再次变化前不再提示。

用户选择“暂时不用”后，状态为 `ready-ignored`，允许创建事件并使用旧侧写。若资料指纹再次变化为不同值，重新进入 `stale-pending`。

首次侧写生成中、资料改动等待确认或重新生成进行中，创建事件都不调用事件 API，并分别提示“导演还在看人设，请稍后再创建事件。”或“角色资料有改动，请先处理人物侧写。”。侧写失败时保留旧侧写（如果存在），显示失败原因和重新生成按钮；没有旧侧写时禁止生成事件。

### 进度

控制台状态区显示当前阶段：`读取人设`、`侧写生成中`、`侧写就绪`、`采集中`、`规划事件`、`规则检查`、`结果提交`。仅在需要用户采取行动、失败或阻止操作时发送系统通知；正常后台阶段通过控制台状态展示。

## 提示词设计

提示词按 intent 拆分，不再用一个事件 JSON system prompt 处理人物侧写。每次请求按“通用人物/事件规则 + 单人卡/多人卡特化 + 主类型/辅助调性特化 + 世界题材 genre + 用户设置和上下文 + JSON 合约”的顺序组装。通用提示词负责项目边界、证据隔离、认知迷雾、用户能动性和 JSON 合约；日常、危机、色情特化提示词只负责改变行动风格、节奏和可用题材。

### 通用提示词规则

通用人物和事件提示词都必须包含以下去阴谋论约束：

- 按 user 的原意、明确行为和实际语气理解，不擅自把普通表达解释成暗示、拒绝、敌意或同意。
- 没有证据时，不把日常巧合、沉默、迟疑、迟到、礼物、偶遇或普通冲突升级为阴谋、跟踪、背叛、组织行动或隐藏身份。
- 区分已证实事实、角色观察到的线索、合理假设、误判和导演幕后信息。假设不能写成事实，误判不能直接作为揭示。
- 需要悬疑或阴谋时，先安排可观察证据和合理的信息获取过程，并保留至少一个普通、非阴谋解释，直到证据足以排除它。
- 不为了制造戏剧性而强行提高风险、扭曲 user 意图、安排角色越权知情或把未同意的用户行动写成已经发生。

所有角色都要有明确动机和“非做不可的事”，且该目标必须需要通过 user 才能完成。角色应主动策划下一步，但必须根据 user 的实际反馈调整；主动推进不等于替 user 决定结果。

### 人物侧写提示词

副 API 根据 `cast.mode` 选择身份。单人卡使用“编剧兼角色策划者”；多人卡使用“编剧兼群像角色策划者”。多人卡不限制角色总数，必须为每个 `cast.members` 成员分别建立资料，不得把多人卡压缩成一个混合人格。

多人侧写除单人字段外，还必须整理：

- 每个角色的主动动机、目标、秘密/执念和必须通过 user 完成的任务。
- 每个角色的明确知道、亲历/可感知、合理推断和明确不知道。
- 角色关系网：已证实关系、关系证据、联盟/敌对/竞争/隐瞒，以及对 user 的共同或不同态度。
- 当前主推手、辅助推手、明面接近者和暗中布局者；没有证据时必须标记为未知或推测。
- 角色之间如何合作、冲突、试探或互相牵制，以及角色暂时不在场时的独立计划。

副 API 收到角色卡和已选世界书条目，输出压缩 JSON：

```json
{
  "content": "压缩人物侧写",
  "citations": [
    { "source": "card:personality", "excerpt": "支持侧写的原文短摘录" }
  ]
}
```

侧写必须覆盖可验证的姓名、性格、背景、与 user 的关系、对 user 的态度、当前目标/秘密/执念、说话风格、适合该角色的主动推动方式，以及角色的知识边界。输出必须区分：明确知道、亲历/当前可感知、合理推断、明确不知道。世界书是导演参考资料，不等于角色全知；没有证据证明角色知道的信息默认属于认知迷雾。

侧写提示词禁止把未来事件规划、其他角色私有知识、未公开伏笔、导演指令或世界书幕后内容直接赋予角色。引用来源单独保存，不能把全部原文复制为侧写正文。

多人侧写不能因为人物数量多而删掉角色的独立目标。低相关角色可以标为候场，但必须保留其计划、关系和知识边界；后续事件从完整角色池选择阶段活跃阵容，不能永久只使用主推手。

### 事件类型特化提示词

生产代码根据设置中启用的类别和权重选择一种主类型。若 user 明确指定类型，则在类别开关、安全边界和硬禁区允许范围内优先遵循；否则对所有已启用且权重大于零的类别归一化，再使用可注入随机源按权重抽取主类型。多个类型组合时必须注明主次和比例，不得把所有类型平均混用。

当前实现虽然已有 `normalizeWeights()`、三个类别设置和权重 UI，但事件生产调用链没有使用归一化权重：模型自行返回 `event.category`，本地 policy 只在响应后检查该类别是否启用。本次必须接通这一缺失的数据流。

抽取结果写入本次请求 intent，模型返回的 `event.category` 必须与主类型一致。其他已启用类别只能作为辅助调性，不能改变主类型的核心结构，也不能绕过自身开关、安全词、硬禁区和重大后果授权。例如可以规划“日常 70% + 亲密 30%”，但 `event.category` 仍为 `daily`；色情类别关闭时不得以辅助调性名义加入色情规划。

同一次创建事件及其人格校验、结构修复重试必须复用同一个类别选择结果，不能重新抽签。用户点击“重新生成”属于新的规划请求，可以重新抽取。世界题材 `genre` 继续表示现实、奇幻、无限流等世界层，不参与日常/危机/色情权重归一化。

**日常情感**：侧重关系升温、轻松互动、暧昧拉扯、情感确认和生活细节。角色可以通过邀约、偶遇、借故求助、制造独处、送礼、共同回忆和小型误会主动推进。伏笔优先使用旧习惯、未说完的话、旧物、重复出现的地点或小承诺；风险和冲突保持可逆、低烈度，除非 user 明确推动升级。

**危机冲突**：侧重外部威胁、悬疑、动作、生存压力、资源约束和限时目标。角色可以安排撤离、护送、临时安全屋、调查、封锁路线、求援、谈判、试探或有限选项。不得把强行带走、伤害、背叛或阴谋当作默认结果；紧迫行动必须给出角色动机、可观察依据和 user 能响应的窗口。危机伏笔可以涉及身份、组织、关键物品或规则，但必须区分事实、线索、假设和误判，并保留普通解释，直到后续证据完成回收。

**亲密张力**：仅在色情类别已启用、相关角色均为成年人、当前 user 授权和安全设置允许时使用。侧重暧昧、情趣扮演、亲密接触借口、私密空间、语言挑逗和双方明确的欲望升级。亲密行动必须保持可撤回，尊重拒绝、安全词和硬禁区；不能把沉默、迟疑或普通礼貌当作同意。导演只规划符合当前授权的阶段，不让角色知道其不应知道的欲望或秘密。

### 事件规划提示词

事件规划继续输出项目已有导演 JSON schema，但必须明确要求：

- 输出完整起承转合和阶段性目标。
- `event.steps` 必须包含 5 到 7 个不同阶段；每个阶段都有唯一 id、角色主动目标、主动活动和结束推进点。
- `foreshadowing` 必须包含 3 到 5 个可在后期回收的伏笔，包含埋设与回收方式。
- 每个关键行动必须绑定当前角色的 `characterId`、人格证据和知识依据。
- 角色可以主动邀请、制造偶遇、布置任务、设置考验、安排活动或执行自己的计划，但行动必须符合其人格、当前地点、关系、能力和已知信息。
- 用户拥有真实反馈和拒绝权；角色可以有下一步计划，但不能把用户尚未同意的行动写成已经发生的事实。
- 不能让角色知道其不应知道的秘密。不同角色的知识必须隔离；导演规划、未来步骤、隐藏伏笔和他人私有信息不得进入角色可见行动依据。
- 认知迷雾应保留为疑问、误判、局部线索或未揭示事实，直到剧情安排了合理的信息获取过程。

为了避免模型因输出上限只生成一个步骤，事件请求提高输出预算并压缩非核心字段；提示词中的 schema 示例展示多步骤数组和伏笔数组的形态，不使用只有 `step-1` 的单步骤示例。JSON 不完整时仍优先缩短文字，不减少要求的步骤和伏笔数量。

### 多人卡事件特化

多人卡使用“编剧兼群像角色策划者”身份。整张卡保留全部 `cast.members` 作为人物池，不把总人数硬限制为 2-4 人；每个阶段只选择 2-4 名与当前场景相关的活跃人物，人数较多时按阶段轮换，避免人物、发言和行动归属混淆。

- 每阶段至少两名活跃人物产生合作、冲突、竞争、试探、隐瞒或联盟变化，不能各说各话。
- 每名活跃人物都必须有自己的阶段目标和主动行动，不能只有一名人物推动、其余人物退化为 NPC。
- 连续阶段不得无理由只使用同一人物。完整 5-7 阶段内，所有与本事件相关的人物都应至少拥有一次明确行动，或受到其他人物行动的实质影响。
- 不在当前场景的人物不得进入本轮 `actions`。其独立计划可以保留在大纲中，但不能被正文模型当作现场事实或其他人物的知识。
- 每个阶段记录 `activeCharacterIds`、各活跃人物的目标与行动、人物间互动、对 user 的单独或集体策划，以及阶段结束推进点。
- 主推手和辅助推手可按阶段变化。主导人物切换必须提供动机、地点和知识状态，不能继承上一名人物的私有知识。
- 多人事件必须生成 4-6 个伏笔，可以分属不同人物或共享；每个伏笔必须说明来源、表面呈现、埋设阶段、回收阶段、回收方式和影响。
- 某个人物暂时不在场时，要保留合理的缺席原因、独立目标和重新介入条件；不能仅因模型遗忘而永久消失。

## 调用顺序和状态

聊天进入/切换后执行：

1. 检查当前是否为非群聊角色聊天和副 API 是否配置完整；单张多人角色卡仍属于可用聊天。
2. 计算当前角色卡与已选世界书的资料指纹。
3. 没有侧写时调用 `profile-character`。
4. 已有 ready 或 ready-ignored 侧写时，仅在指纹变化时标记 `stale-pending`。
5. 用户点击重新生成后调用 `profile-character`，成功才更新侧写和 active fingerprint。
6. 用户点击暂时不用后保存 ignored fingerprint，状态转为 `ready-ignored`。
7. 事件创建只有在侧写状态为 `ready` 或 `ready-ignored` 时才调用 `plan-event`。
8. 事件请求前确定主类型和允许的辅助调性，并在该请求及其重试中固定类别选择结果。

同一聊天的侧写请求必须去重。切换聊天或角色时取消旧的后台结果，避免旧请求覆盖新聊天状态。副 API 请求失败时保存脱敏错误信息，不泄露 API Key、授权头、聊天私密内容或世界书完整原文。

## 兼容性与状态迁移

新增字段必须通过默认状态和迁移提供：

- `personalityProfile.activeFingerprint`
- `personalityProfile.ignoredFingerprint`
- `personalityProfile.status` 支持 `empty`、`generating`、`ready`、`stale-pending`、`ready-ignored`、`failed`

旧的 `ready` 侧写若没有 active fingerprint，可根据现有 fingerprint 兼容读取；不能把已有侧写强制丢弃。API Key 继续只保存在全局扩展设置。

## 测试与验收

自动测试必须覆盖：

1. 人物侧写使用独立提示词和 profile schema。
2. 事件提示词硬性要求 5-7 个步骤、3-5 个伏笔和认知迷雾。
3. 多人侧写保留全部人物并隔离每人的证据、关系和知识边界。
4. 多人事件每阶段使用 2-4 名活跃人物、5-7 个阶段和 4-6 个伏笔，并轮换相关人物。
5. 通用提示词包含去阴谋论规则，三类特化不会凭空升级事件规模或曲解 user 意图。
6. 类别权重实际参与主类型抽取；禁用和零权重类别不会被选择。
7. 同一次事件请求及其修复重试保持主类型不变，重新生成才重新抽取。
8. 辅助调性不能绕过禁用类别、色情安全边界或本地 policy。
9. 未配置副 API 时不调用主 API，并产生配置提示。
10. 进入聊天后首次侧写只调用一次副 API。
11. 侧写完成前创建事件不会调用事件 API。
12. 资料变化进入 `stale-pending`，不自动请求，并显示重新生成/暂时不用操作。
13. 暂时不用后使用旧侧写且不重复提示；资料再次变化后重新提示。
14. 重新生成成功后更新指纹，允许事件规划。
15. 失败时保留旧侧写并提供重试。
16. 现有事件生命周期、API 响应解析、世界书选择和入口回归测试继续通过。

真实 SillyTavern 验收必须确认：进入聊天的副 API 请求顺序为人物侧写在前、事件规划在后；人物页的两个 stale 操作行为正确；配置缺失、侧写生成中和失败状态的提示可见；调整类别权重后主类型抽取符合预期且禁用类别不出现；单人和多人事件页面都显示至少 5 个步骤；多人阶段不会挤入全部人物或长期遗忘相关人物；日常随机事件不会无依据升级为阴谋或危机；角色正文中不会直接暴露未公开幕后信息。
